Fire Harmonizer: how it actually works

Two block diagrams: how a raw satellite detection becomes a plain-language anomaly alert, and which component talks to which when a user asks for one region and date range. Built on real NASA FIRMS data (MODIS + VIIRS), demoed against the Sept 2026 Kazakhstan steppe fires.

1. Data & processing pipeline

What happens to a satellite detection between the satellite and the screen. Five hops, each one a real transformation — this is the order judges will ask about if they ask "how is it actually harmonized."

2. Request flow — who talks to whom

One user action — pick a region and a date range — and the four network hops it triggers. The harmonization and z-score math happen inside the backend process, not over the network, which is why they're a label, not an arrow.

Codex builds: harmonization + anomaly math, backend endpoints

Shared / external: data sources, UI shell

Data source: NASA FIRMS (Fire Information for Resource Management System), which already serves both MODIS and VIIRS active-fire detections — our harmonization layer is the normalization step on top of that, not a new sensor calibration. Anomaly engine: a transparent seasonal z-score, cross-checked against a real Isolation Forest model (scikit-learn, ml/anomaly_model.py) run offline — two independent methods agreeing is the validation, not a single black-box score. Local validation case: the September 2026 Kazakhstan steppe and forest fires (~2,870 ha).
